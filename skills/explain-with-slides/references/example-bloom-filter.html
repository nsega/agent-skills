How Bloom filters work

1 / 1
01 · What it is

A Bloom filter answers “have I seen this?” with bits, not the items

Notes

Start on the left 1. A hash set answers membership exactly because it keeps every key it has seen, in full. For a million email addresses that means the addresses themselves plus the table's own overhead, so its memory grows with the size of the keys, not only their count.

The right side 2 is the whole Bloom filter: one array of bits, sized up front, with no keys stored anywhere. Instead of remembering items, it remembers a few bit positions per item. Its size therefore depends only on how many items you expect and how wrong you are willing to be, never on how long each key is. At a 1% false-positive rate it needs about 9.6 bits, roughly 1.2 bytes, per key, whether the key is an 8-byte ID or a 2 KB URL.

The price is the answer itself. A hash set says yes or no. A Bloom filter says definitely not or probably yes. The next three slides show where that asymmetry comes from.

A Bloom filter is not a compressed hash set. You cannot list, retrieve or count the items in it, because the items were never stored.

02 · How it works

Adding an item sets k bits, chosen by k hash functions

Notes

Read the figure top down. The item 1 goes through k hash functions, here three, and each one picks a position in the array. Adding the item sets those positions to 1 2. Nothing else is written, and setting a bit that is already 1 changes nothing.

In practice you rarely run k separate hash functions. The usual trick, from Kirsch and Mitzenmacher, derives all k positions from two base hashes: position i is h1 + i * h2 mod m. It performs as well as k independent hashes for two hash computations per operation.

import hashlib

class Bloom:
    def __init__(self, m, k):
        self.m, self.k, self.bits = m, k, bytearray(m)

    def _positions(self, item):
        d = hashlib.sha256(item.encode()).digest()
        h1 = int.from_bytes(d[:8], "big")
        h2 = int.from_bytes(d[8:16], "big") | 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, item):
        for p in self._positions(item):
            self.bits[p] = 1

    def might_contain(self, item):
        return all(self.bits[p] for p in self._positions(item))

This toy spends a whole byte per bit to stay readable. Real implementations pack the bits.

More hash functions is not better. Each extra hash sets more bits, so the array fills faster. The best k for a given size is about (m / n) * ln 2, which is 7 at the 1% setting.

03 · How it works

A lookup checks the same k bits, and any 0 means definitely absent

Notes

A lookup recomputes the same k positions an add would, then reads them. Here "dog" lands on positions 2, 5 and 13. Position 2 is 1, set earlier by "cat", but position 5 is 0 1.

That single 0 is conclusive 2. If "dog" had ever been added, all three of its positions would have been set, and a plain Bloom filter never clears a bit. So a 0 at any of the item's positions proves the item was never added. There are no false negatives.

This is the half of the answer you can build on. Most real uses are shaped around it: the filter's job is to say no quickly so you can skip work, and a no is always right.

A lookup can also stop at the first 0 it finds. Queries for absent items, the common case in most uses, are therefore usually cheaper than queries for present ones, which must check all k bits.

No false negatives holds only for the filter as built. If you rebuild it from a partial data set, or two services hash the key differently (another seed, another string encoding), you will get false negatives, and they are silent.

04 · How it works

All 1s only means “probably present”, because other items may have set those bits

Notes

The filter now holds "cat" and "fox", and the labels under the array show which item set each bit. Look up "owl", which was never added. Its positions are 2, 9 and 14 1. Position 2 was set by "cat", positions 9 and 14 by "fox". Every bit the lookup checks is 1, so the filter answers probably present 2, and it is wrong.

This false positive is built into the design. The filter keeps no record of which item set which bit, so it cannot tell "owl's bits are set" apart from "other items happened to set owl's bits". As more items go in, more bits are 1, and collisions like this get more likely.

The useful framing is that a yes from a Bloom filter means go check. Whatever sits behind the filter, a disk read, a network call or a database query, has to confirm the answer. The filter only decides whether that check is worth doing.

This is not a collision between two whole items. "owl" collides with neither "cat" nor "fox". Each of its bits collides with some bit of some other item, which is why the rate depends on how full the array is, not on hash quality alone.

05 · Tuning

The false-positive rate is a dial you set with bits per key

Notes

The horizontal axis is the memory you spend, in bits per stored key. The vertical axis is the false-positive rate on a log scale, assuming the best number of hash functions for each size. On a log scale the curve is a straight line: every extra 4.8 bits per key cuts the error rate by 10x.

Two points are worth remembering. About 9.6 bits per key gives 1% 1, with 7 hash functions. About 14.4 bits per key gives 0.1% 2, with 10. Going from 1% to 0.1% costs 50% more memory, not 10x more.

The sizing formulas, for n expected keys and a target rate p:

m = -n * ln(p) / (ln 2)^2    total bits
k = (m / n) * ln 2           hash functions

For 10 million keys at 1%, m is about 96 million bits, roughly 12 MB, and k is 7.

The n in those formulas is a promise. Size for 10 million keys, insert 30 million, and the array saturates: the false-positive rate climbs far above the target. Size for the largest n you expect, or use a scalable variant that adds layers as it grows.

The rate is per lookup of an absent key. A request path that does 1,000 such lookups at 1% should expect about 10 wasted checks behind the filter, not zero.

06 · When to use it

Put one in front of an expensive lookup, not in place of it

Notes

This is the most common shape in production. A read for a key asks the in-memory Bloom filter first. When the filter says definitely absent 1, the system returns "not found" without touching the disk. Only a maybe pays for the expensive read 2, and a false positive costs exactly one wasted read, never a wrong answer, because the disk is still the source of truth.

Log-structured storage engines are the classic example. Bigtable, Cassandra and RocksDB keep data in many immutable sorted files (SSTables) and keep a Bloom filter for each one. A point read for a key that lives in one of twenty files would otherwise open all twenty. With filters at 1%, it checks twenty small in-memory filters and reads, on average, about one file.

The same shape appears wherever an exact check is slow and most answers are no: a crawler skipping URLs it has already fetched, a cache tier skipping a backend call for keys that do not exist, a join skipping probes for rows that cannot match.

Do not put the filter in front of a check you skip on yes. If probably present leads straight to an action, such as rejecting a username as taken, false positives become real errors for real users.

07 · Compared with alternatives

Plain Bloom filters can't delete, so pick a variant when you need to

Notes

Each column is a filter you might reach for. The plain Bloom filter cannot delete 1: clearing an item's bits would also clear bits other items share, which creates false negatives, the one error the structure promised never to make.

A counting Bloom filter replaces each bit with a small counter, usually 4 bits. Add increments, delete decrements, and a position counts as set while its counter is above zero. Deletion works, at about 4x the memory of the plain filter, and only for items that were really added. Deleting something that was never inserted corrupts the filter.

A cuckoo filter stores a short fingerprint of each item in one of two candidate buckets. It supports deletion, reads at most two buckets per lookup, and for target rates below about 3% it uses less space than a space-optimal Bloom filter 2, according to Fan et al. Its catch is that inserts can fail as the table gets close to full, so it needs headroom.

None of these grow freely. When n is unknown, look at scalable Bloom filters, which chain filters of increasing size, or rebuild periodically from the source of truth.

If you want deletes only to expire old data, it is often cheaper to rotate filters, for example one per day, and drop the oldest, than to switch structures.

08 · Summary

Use one where “maybe” is cheap to check and “no” saves work

Notes

The whole idea fits in the figure. Adding an item sets k bits. A lookup reads the same k bits: any 0 means the item is definitely absent, and all 1s means it is probably present. How often "probably" is wrong is a dial you set with memory, about 9.6 bits per key for 1%.

Reach for a Bloom filter when three things hold: you can afford to confirm a yes with a slower exact check, most lookups are for things that are not there, and the memory or bandwidth for the exact set is the real constraint. If any of them fails, a hash set or a sorted index is simpler and exact.
